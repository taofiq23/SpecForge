## 1. Executive summary

The Space Fractions system is a web-based, interactive learning tool designed to improve
fraction-solving skills for sixth-grade students. The system consists of an introductory
movie, a main menu, a series of fraction questions, and an ending scene with feedback.

- **Architectural style:** Microservices
- **Deployment topology:** Cloud-based infrastructure
- **Traceability:** see `traceability_matrix.csv` (FR-1, NFR-1, ASR-1)

## 2. Components

The spec names three components. Each is a separately deployable service with its own
process, its own schema, and its own API surface. The spec's diagrams additionally name an
`AdminComponent` (ComponentDiagram) with an `Admin` actor (UseCaseDiagram, ClassDiagram), and two
client nodes `UserClient` / `AdminClient` (DeploymentDiagram). **All three of these are built as
real artifacts** — the AdminComponent as a real module, and the two clients as the real frontend
under `web/` — not left as open questions.

| Component | Responsibility (spec §C/§D) | Owns | Code |
| --- | --- | --- | --- |
| **GameComponent** | Game logic and user interaction | `game.games` (game state JSONB) | `services/game` |
| **QuestionComponent** | Question management and data persistence | `question.questions` | `services/question` |
| **UserComponent** | User authentication and authorization | `user_svc.users`, `user_svc.refresh_tokens` | `services/user` |
| **AdminComponent** | Admin surface: Update Questions (UseCaseDiagram), §G game stats | none — composites over `question.questions` | `services/admin` |

Each component's entry point is a class literally named after the component
(`GameComponent`, `QuestionComponent`, `UserComponent`, `AdminComponent` in
`services/*/src/component.js`), so every name in the traceability matrix resolves to a real symbol.
The class/domain layer beneath it carries the ClassDiagram's names (`Game`, `Question`, `User`,
`Admin`, `GameService`, `QuestionService`, `UserService`).

**AdminComponent** (`services/admin/`) is a real module with its own class, routes
(`src/routes/adminRoutes.js`), application layer (`src/service/adminService.js`), and an optional
standalone entry point (`src/server.js`, `ADMIN_PORT` 8084). It owns no tables — the ClassDiagram
makes `Admin --* Question` a composition, so admin writes are proxied to QuestionComponent as
SequenceDiagram2 draws them. It is **hosted inside the GameComponent process by default**
(`adminComponent.mountOn(app)` under `/api/v1/admin`) and can also be booted standalone to scale the
admin surface apart from the game. See README §5.6.

**The frontend** (`web/`) realises the DeploymentDiagram's `UserClient` and `AdminClient` nodes as
real, tested pages served as static files by GameComponent (`services/game/src/routes/uiRoutes.js`),
with no framework and no build step:

| Node | Files | Served at |
| --- | --- | --- |
| **UserClient** | `web/index.html`, `web/app.js`, `web/styles.css` | `GET /` (and `/play-ui`) on GameComponent |
| **AdminClient** | `web/admin.html`, `web/admin.js`, `web/styles.css` | `GET /admin` (and `/admin.html`) on GameComponent |

The browser talks to the same origin, which is exactly the `GameServer -- UserClient` /
`GameServer -- AdminClient` edges. `GET /ui-config.js` injects `window.SPACE_FRACTIONS_CONFIG` at
runtime so the pages can be repointed at another API origin without a rebuild, and `uiRoutes.js`
also exposes a same-origin `POST /oauth/token` proxy so the AdminClient sign-in form can reach
UserComponent across origins. Framework choice was not specified by the spec; plain HTML/CSS/JS was
chosen. See README §5.6.

### 2.1 Component interactions

From ComponentDiagram / DeploymentDiagram / ContainerDiagram — every edge below is a real,
built connection (static hosting, a mounted router, or an HTTP call), not a plan:

```
GameComponent   -- QuestionComponent   (REST: prompt + answer checking)
GameComponent   -- UserComponent       (REST: token validation / authorisation)
GameComponent   -- AdminComponent      (AdminComponent is hosted in-process; its router is
                                        mounted under /api/v1/admin on GameComponent)
GameComponent   -- UserClient          (serves web/index.html + web/app.js + web/styles.css)
GameComponent   -- AdminClient         (serves web/admin.html + web/admin.js; proxies
                                        POST /oauth/token to UserComponent)
```

The two client edges are realised by `services/game/src/routes/uiRoutes.js` (`createStaticUIRoutes`)
mounted from `GameComponent.buildApp()`, and AdminComponent by
`AdminComponent.mountOn(app)`. `AdminComponent -- QuestionComponent` (the admin's data edge) is drawn
in the ComponentDiagram as `GameComponent -- AdminComponent`; AdminComponent reaches
QuestionComponent through the same REST client GameComponent uses.

Plus the asynchronous edge implied by §D ("Messaging: RabbitMQ 3-4"): GameComponent and
QuestionComponent publish domain events; UserComponent consumes them for the §G
"user engagement" metric.

## 4. Data model

Schemas are separated per component (database-per-service discipline). The spec's DDL
statements are reproduced verbatim in the DDL files and extended only where the generated
code needs a column the spec omitted (each extension is commented in place).

- `sql/game_ddl.sql` — spec §D `games (id SERIAL, game_state JSONB)` + `game_uid UUID` +
  `updated_at`, indexes for §G reporting, and the ASR-1 standby role/grants.
- `sql/question_ddl.sql` — `question.questions` with `question_uid`, `prompt`, `options`,
  `correct_option`, `difficulty`, `weight`, `tags`, `active`, `version`.
- `sql/user_ddl.sql` — `user_svc.users` (password hash + salt, role, active) and
  `user_svc.refresh_tokens` (hashed, rotating, revocable).
- `sql/00_bootstrap.sql` — schemas + `pgcrypto`.

## 5. Interface design

- **External API:** `openapi.yaml` — OpenAPI 3.0. The spec's single `/play` path is
  reproduced byte-for-byte at the top; every route the generated services actually serve
  is documented below it under an explicit "not in the spec" banner.
- **Internal contracts:** `internal.proto` — the spec's `spacefractions.GameService.Play`
  gRPC contract, verbatim. The services expose the same operations over REST; the proto
  file is the canonical internal contract and is kept in sync by the `npm run proto:gen`
  script in the root `package.json`.

## 6. Caching and consistency

§D: "Cache game state in Redis / Use PostgreSQL for data persistence / Implement data
replication for high availability."

- **Cache-aside** (`shared/src/db/redis.js`) in front of PostgreSQL. Reads go to Redis
  first, then PostgreSQL, then rehydrate the cache.
- **PostgreSQL is authoritative.** A cache miss or a Redis outage degrades latency, never
  correctness — the repository falls through to PostgreSQL on any Redis error.
- Game and question writes persist to PostgreSQL and invalidate/refresh the cache
  afterwards (write-through on the record just saved).
- Readiness probes (`/ready`) mark PostgreSQL `required: true` and Redis/RabbitMQ/
  Elasticsearch `required: false` for exactly this reason.

## 7. Deployment

`k8s/spacefractions-deployment.yaml` contains, in one file:

1. The spec §E snippet, verbatim, between `--- spec-snippet-start ---` and `--- spec-snippet-end ---`.
2. Namespace `spacefractions` with `istio-injection: enabled` (service mesh, §F).
3. ConfigMap + Secret for all component configuration; secrets are placeholders for Vault.
4. Deployments + Services + HPAs for `game-component`, `question-component`,
   `user-component`, each with liveness/readiness probes, resource requests/limits, and a
   locked-down `securityContext` (`runAsNonRoot`, `readOnlyRootFilesystem`, all caps dropped).
5. TLS Ingress (§F) routing `/play` and `/api/v1/games` → game, `/api/v1/questions` and
   `/api/v1/durability` → question, `/oauth` and `/api/v1/users` → user.
6. Default-deny NetworkPolicy + an explicit allow rule for the component mesh (§F threats).
7. PostgreSQL 14 StatefulSet (3 replicas, `--data-checksums`) with a headless Service.
8. Redis 6, RabbitMQ 3, Elasticsearch 7, Prometheus 2 workloads.
9. PodDisruptionBudgets for the two critical components, honouring §G's availability targets.

`docker-compose.yml` provides the same topology locally; `Dockerfile` builds each service.

### 7.1 DB HA topology (§E)

- PostgreSQL streaming replication to at least one standby; `game_ddl.sql` creates a
  read-only `spacefractions_standby` role used both by the replication check and the DR runbook.
- Regular backups: hourly snapshot cadence recorded as a schema comment, driven externally.
- ASR-1 is verifiable at runtime via `GET /api/v1/durability`, which reports replica count,
  WAL recovery point, persisted row count, and the RPO/RTO targets.

## 8. Security (§F)

- **AuthN/AuthZ:** OAuth2. UserComponent acts as the authorization server
  (`POST /oauth/token`) supporting the password, `client_credentials`, and `refresh_token`
  grants. Components validate JWT bearer tokens and enforce scopes/roles.
- **Password storage:** salted hash, never reversible; comparison is constant-time and a
  dummy hash is computed for unknown usernames to prevent enumeration.
- **Refresh tokens:** random 48-byte values, stored hashed, rotated on every use, revocable,
  and purged on expiry.
- **Secrets management:** Vault is the intended store (`REPLACE_WITH_VAULT_VALUE`
  placeholders in the Secret); rotation policy is reflected in refresh-token rotation and
  documented in the manifest.
- **TLS:** enforced at the Ingress with SSL redirect; Istio provides mTLS inside the mesh.
- **Threat model:** the top 5 threats from §F — unauthorized access, data breaches, denial
  of service, malware, phishing — are mitigated by bearer auth + scope checks,
  encryption in transit, HPAs + PDBs + resource limits, non-root read-only containers, and
  the NetworkPolicy default-deny.

## 9. Observability, SLOs and operations (§G)

- **Per-component/business metrics:** GameComponent — game start rate, game completion rate,
  user engagement; QuestionComponent — question response rate, question accuracy rate.
  Exposed via `prometheus-client` on `/metrics` (`shared/src/observability/metrics.js`).
- **SLO:** 99.99% uptime. **Error budget:** 1%. **RTO:** 1 hour. **RPO:** 1 hour.
  The RTO/RPO values are surfaced by the `/api/v1/durability` endpoint.
- **Scrape config:** `ops/prometheus.yml` + `ops/prometheus-rules.yml` (local), and an
  equivalent in-cluster ConfigMap in the k8s manifest.
- **Runbook hooks:** `POST /internal/seed` on QuestionComponent (recovery after restore),
  `GET /internal/engagement` on UserComponent, `/health` and `/ready` on every component.

## 10. Design risks and mitigations (§A)

| Risk | Mitigation | Where it lives |

## 13. Assumptions and open questions (§K)

**Assumptions**

- **A1:** The game will be played by 1000 users concurrently → drives HPA `minReplicas: 3`
  / `maxReplicas: 20` and the resource requests in the manifests.
- **A2:** The game will be played for 1 hour per session → drives the 3600s redis game-state
  TTL and the `userEngagementSeconds` metric.

**Unresolved stakeholder questions needing input**

- What is the expected user growth rate?
- What is the expected game session length?

## 14. Migration plan (§I)

1. Migrate game data to the new database.
2. Update game logic to use the new database.
3. Deploy the new game component.

Data sync uses replication plus an external sync tool (Apache NiFi per §I). Public API
backwards compatibility is maintained for 1 year with a 1-month migration window. The
`game_uid`/`game_state` split in `sql/game_ddl.sql` exists partly to make step 1 a
non-breaking copy. Rolling deploys are supported by the PDBs and rolling-update defaults.
